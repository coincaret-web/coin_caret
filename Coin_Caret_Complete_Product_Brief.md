# Coin Caret Complete Product Brief

**Product:** Coin Caret (`CC`)  
**Document status:** Design and development brief  
**Version:** 1.0  
**Date:** 16 September 2026  
**Primary launch surface:** Responsive web  
**Later surfaces:** Android and iOS applications

---

## 1. Executive summary

Coin Caret is a realistic cryptocurrency-wallet simulation platform. It lets users create a simulated wallet, hold the platform’s simulated currency, Coin Caret (`CC`), send and receive CC, view pending and confirmed transactions, explore simulated blocks, and learn how wallet mechanics work in context.

It is **not a cryptocurrency exchange, custodial real-asset wallet, payment service, blockchain, or investment product**. CC has no monetary value, cannot be redeemed, bought, sold, exchanged, or withdrawn to an external wallet, and does not settle on any public or private blockchain. All balances, fees, addresses, transactions, blocks, and confirmations are records within the Coin Caret simulation service.

The goal is a polished, credible financial-product experience without concealing those facts. The interface should feel modern and operational, while clear, proportional disclosures remain visible at moments where a reasonable person might otherwise assume real value or real settlement.

### Product model

```text
Public site          Wallet web app          Admin console
coincaret.com        app.coincaret.com       admin.coincaret.com
      │                       │                        │
      └───────────────────────┼────────────────────────┘
                              │
                    Coin Caret API / services
                              │
                  Authoritative simulated ledger
                              │
         Simulated assets, wallets, transactions, blocks, fees
```

The browser is never authoritative for balances or transaction results. The backend validates every operation, records double-entry ledger postings atomically, and exposes only permitted data.

## 2. Product goals and non-goals

### Goals

- Deliver a highly understandable, professional wallet experience using simulated CC.
- Let a user safely experience the core sequence: obtain CC → receive address/QR → send → pending status → confirmations → explorer → final balance/history.
- Give administrators controlled ways to issue CC, manage users, configure the simulation, moderate requests, and audit all sensitive actions.
- Make simulation status clear without turning the product into a dense educational website.
- Establish a single API and ledger suitable for web first and mobile later.
- Build an extensible asset model so future simulated assets can be added without redesigning the ledger.

### Non-goals for V1

- Real cryptocurrency, token issuance, wallets, keys, seed phrases, custody, on-chain transactions, fiat deposits, card payments, trading, staking, lending, yields, swaps, or conversion.
- External blockchain RPCs, mainnet/testnet integration, external wallet connection, or external withdrawals.
- Claims that CC has a market price, investment value, backing, liquidity, or redeemability.
- Real KYC/AML flows unless the legal model later requires them; do not present a cosmetic identity check as real compliance.
- Native mobile apps in the web V1 delivery.

## 3. Product positioning and communication rules

### Positioning

**Recommended primary message:** “Experience how crypto wallets work—using simulated CC, not real money.”

Coin Caret is a hands-on digital-asset simulation environment. It is a simulation product first, with a realistic wallet interface and contextual learning layer.

### Required truth-in-product rules

- Use **simulated**, **practice**, or **simulation network** in onboarding, footer, wallet context, transaction review, explorer, demo mode, and legal pages.
- Never label an internal transfer as “on-chain,” “mainnet,” “blockchain settlement,” “deposit,” or “cash-out.” Preferred terms are **simulated transfer**, **wallet credit**, **issue CC**, **request simulated withdrawal**, and **simulation transaction**.
- A simulated price, if enabled, must be called a **display value** or **simulation reference value**. It must never imply a quote, market price, conversion rate, or value guarantee.
- Wallet addresses are platform identifiers, not public-chain addresses. Include “Coin Caret Simulation Address” near the copy/QR controls.
- Do not use copy that says “trade,” “earn,” “invest,” “withdraw to bank,” “secure your assets,” or “your crypto” unless explicitly qualified and legally approved.
- The product may use realistic transaction states and blocks as teaching metaphors, but should explain that those are generated by Coin Caret’s internal simulation ledger.

### Disclosure placement

| Location | Required disclosure |
|---|---|
| Footer, every public page | “CC is simulated, has no monetary value, and cannot be redeemed or transferred outside Coin Caret.” |
| Sign-up | Acceptance of Terms plus concise simulation disclosure |
| First dashboard visit | Dismissible education banner, persisted as acknowledged |
| Send review and confirmation | “This is a simulated transfer inside Coin Caret. No real crypto is sent.” |
| Receive screen/QR | “Only use this address within Coin Caret.” |
| Withdrawal request | “Withdrawal is a simulated learning workflow; no external transfer occurs.” |
| Explorer | “Explorer data represents the Coin Caret Simulation Network, not a public blockchain.” |
| Demo | “Temporary simulation. Data may reset and has no value.” |

## 4. Target users and priority use cases

### Primary users

1. **Curious beginner** — wants to understand wallet terminology and observe a transaction without financial risk.
2. **Guided learner** — follows a course, workshop, or instructor-led exercise.
3. **Demonstrator** — uses a polished product experience to explain wallet flows to an audience.
4. **Administrator/instructor** — provisions CC, controls exercises, reviews activity, and supports participants.

### Core jobs to be done

- “I want to practice receiving and sending a digital asset without using money.”
- “I want to see why a transaction has a fee and why confirmation takes time.”
- “I want to trace a transaction and understand an explorer.”
- “I want to set up a classroom or demonstration and give participants simulated balances.”
- “I want to operate a safe, controlled simulation without manually changing balances.”

### Primary V1 scenarios

1. Visitor explores public site, enters demo mode, receives a temporary wallet and sends CC to a seeded demo recipient.
2. Registered user verifies email, receives an initial CC grant or an admin-issued credit, then sends CC to another registered user.
3. User uses a QR code to fill a recipient address and completes a send flow with configurable fee and confirmations.
4. User opens a transaction in Explorer and watches status advance from queued to confirmed.
5. Admin creates a training cohort, issues CC with a reason, monitors transactions, and reviews the audit trail.

## 5. Brand and UI direction

### Personality

Clear, precise, calm, capable, and modern. It should resemble a trustworthy fintech dashboard, not a casino, hype-token site, or generic classroom portal.

### Visual direction

- Dark navy/graphite base with optional light mode; high-contrast neutral surfaces.
- A distinctive but restrained accent color (for example teal or indigo), plus semantic success, warning, and error colors.
- Clean grotesk/sans-serif type, tabular figures for balances, and generous spacing.
- Transaction and network concepts represented through cards, timelines, status chips, and subtle motion—not noisy 3D coin graphics.
- Display simulated status through a compact, persistent “Simulation Network” badge; do not rely on color alone.
- Use positive green only for confirmed/received outcomes; avoid green as a universal “money” cue.

### Tone of voice

- Plain English before technical language; put definitions behind tooltips or “Learn why” links.
- State outcomes directly: “Transaction queued,” “3 of 3 confirmations complete,” “Insufficient simulated CC for amount and fee.”
- Avoid certainty where the engine is still processing: say “Estimated confirmation time” rather than “will confirm in.”

## 8. Account and authentication flows

### Registration

1. User selects Create account.
2. Enters email, password, legal name/display name policy fields, country only if justified, and consent.
3. Sees concise simulation disclosure and Terms/Privacy links.
4. System creates an unverified account and sends a verified-email link.
5. After verification, system provisions default CC wallet and presents welcome/onboarding.
6. Optional invite/cohort code may determine initial credit policy.

### Login and session rules

- Email/password login; passwordless magic link can be added later.
- Rate limit sign-in, password reset, email verification, and resend operations.
- Admin accounts require MFA from first launch; consider MFA for user actions above a configured simulation threshold.
- Show recent session/device history and enable user-initiated session revocation.
- Use secure, HttpOnly, SameSite cookies for browser sessions; do not store long-lived access tokens in `localStorage`.

### Recovery and account lifecycle

- Forgot password: time-limited, single-use verified-email link; invalidate existing sessions after reset or offer explicit choice.
- Change email: confirm on both old and new addresses where feasible.
- Suspend: user cannot sign in or transact; data is retained according to policy.
- Delete/export request: queued, authenticated, and reviewed according to applicable law. Explain ledger/audit records that may be retained for security and integrity.

### Onboarding sequence

1. Welcome and “simulation, not real value” disclosure.
2. Explain CC wallet, address, and safe practice environment.
3. Show wallet address and QR.
4. Invite first action: explore demo walkthrough, request training CC, or receive from another user.
5. Track completion, but permit skip.

## 9. Wallet, address, QR, and transaction flows

### Simulation address

- Generate opaque, non-guessable, checksummed identifiers, for example `CCS1-7K4P-9M2X-...`; do not mimic a real chain’s address format.
- Each address belongs to exactly one wallet. V1 can use one reusable address per wallet; future versions may support address rotation.
- Do not expose email, real name, or internal user ID through the address or public Explorer.
- Address UI includes copy, QR, share, and a statement that it works only within Coin Caret.

### Receive

1. User opens Receive and chooses CC wallet.
2. Screen shows address, QR code encoding only the simulation address/deep-link data, and copy/share controls.
3. Optional request amount/note produces a request URI/QR; neither should create a financial obligation.
4. When a matching transfer confirms, recipient sees a notification and activity entry.

### Send

1. User chooses CC wallet and enters/pastes/scans recipient simulation address.
2. Backend validates address format and active destination wallet; client never decides validity alone.
3. User enters positive amount and optional note subject to limits.
4. Backend returns an authoritative fee quote, total debit, available balance, rules, expiry, and simulation disclosure.
5. Review screen shows recipient address/label, amount, fee, total, estimated confirmation time, and “No real crypto is sent.”
6. User confirms; require reauthentication/MFA if policy triggers.
7. Server atomically creates transaction plus pending ledger reservations; returns internal transaction ID and queued status.
8. Processor assigns block and confirmation progression; completion/failure is delivered in app and by notification preference.

### Simulated withdrawal request

The term “withdrawal” is allowed only with explicit qualifier. It demonstrates a request/review lifecycle but **never transfers externally**.

1. User opens “Request simulated withdrawal.”
2. Explainer states the result is a simulation record, not an external transfer.
3. User selects amount, optional destination scenario/template, and purpose.
4. Eligibility and balance are checked. The request may be auto-approved or reviewed by an admin based on simulation policy.
5. On approval, a simulated outbound transaction is created to a designated sink/training destination; on denial/cancellation, reserved funds are released.

### Cancellation, replacement, and failure

- Before a transaction is assigned to a block, user may request cancellation only if simulation settings permit; show likelihood and deadline.
- Do not mutate a confirmed transaction. Use a compensating adjustment/reversal transaction with a clear relationship to the original.
- A failed/expired transaction releases the reserved amount and fee as applicable. Every outcome stays in history.
- Do not offer “speed up” or “replace by fee” in V1 unless carefully modelled as a simulation lesson.

## 10. Simulated ledger, network, block, fee, and confirmation mechanics

### Core principle: internal, append-only accounting

Use an immutable double-entry ledger. A current balance may be cached for reading performance, but the ledger is the source of truth and all writes are atomic database transactions.

For a user-to-user send of 100 CC with a 0.50 CC fee:

```text
Sender available account            -100.50 CC
Recipient available account         +100.00 CC
Simulation fee account              +  0.50 CC
```

During pending state, post/reserve funds in a dedicated pending account or record an immutable reservation; prevent double spending. On confirmation, finalize the postings. On failure, release/reverse the pending reservation using explicit entries.

### Transaction states

```text
draft → quoted → submitted/queued → block_assigned → confirming → confirmed
                                  └→ rejected | failed | expired | cancelled
```

State transitions are validated server-side and logged. `confirmed` is terminal except for a separately-created administrative compensating transaction.

### Default simulation configuration (admin configurable)

| Parameter | Default | Notes |
|---|---:|---|
| Asset | CC | Simulated only |
| Initial display value | 1 CC = 1 simulation unit | Optional display aid, not a market price |
| Fee model | Flat 0.50 CC | Can later support percentage/minimum cap |
| Block interval | 10 seconds | Background processor target, not a guarantee |
| Required confirmations | 3 | Transaction becomes confirmed after third block including/after assignment per published rule |
| Max send amount | Configurable | Per user/cohort/role limits |
| Daily send limit | Configurable | Simulation safety/control rule |
| Address model | One active address/wallet | Future rotation allowed |

### Block simulation

- A scheduled worker creates monotonically increasing simulated blocks when the network is operational.
- Each block stores height, synthetic hash, previous synthetic hash, created timestamp, status, and transaction count. Hashes are identifiers for teaching/UI only, not cryptographic chain security claims.
- Eligible queued transactions are selected deterministically (for example FIFO, then priority policy) and assigned to the next block within capacity.
- The confirmation worker increments confirmation count for relevant transactions as later blocks are created.
- Pause mode stops block creation/confirmation and exposes a public “Simulation Network maintenance” state; new sends should be disabled or queued per selected policy.

### Fees

- Fee quote is calculated server-side against the active fee schedule and is locked for a short expiry.
- Show fee and total debit before confirmation.
- Specify whether a failed transaction consumes no fee (recommended V1) and apply it consistently.
- Fees credit a dedicated internal simulation-fee account, not a real business revenue or user withdrawal balance.

### Issuance and supply

- CC supply is an internal accounting concept. A protected `reserve/issuance` account is the source for admin credits.
- Admin issuance requires a reason, amount, recipient/cohort, and permission; optional approval threshold for large amounts.
- “Total issued,” “circulating,” “held in reserve,” and “burned/retired” definitions must be documented and calculated from ledger accounts.
- Never describe supply figures as blockchain-verified or market capitalization.

## 11. Explorer requirements

### Search and browse

- Search by internal transaction ID, simulation address, or block height/synthetic hash.
- Use safe partial-match behavior; return no result without revealing whether a private account exists beyond public address records.
- Browse latest blocks and latest public-safe transactions. Default transaction rows truncate addresses and never show private notes, user emails, IPs, sessions, or admin-only metadata.

### Explorer pages

- **Explorer home:** Search, current network status, block height, latest blocks, latest transactions, and simulation notice.
- **Transaction detail:** status timeline, ID, amount, fee, total debit, from/to simulation addresses, assigned block, confirmations, timestamps, and notice.
- **Address detail:** public address, asset balance only if public-visibility policy permits, transaction list, and privacy notice. V1 recommendation: show address activity but not a direct identity.
- **Block detail:** height, synthetic hash, prior/next links, creation time, transaction count, transactions, and block-generation explanation.

### Privacy choice

Default to a **pseudonymous Explorer**: simulation addresses and transaction facts are public within the product, while identity mappings remain private. Include this in onboarding and privacy terms.

## 12. Demo mode and learning layer

### Demo mode

- Available without a permanent account, using a segregated demo tenant/ledger namespace.
- Provide a pre-funded temporary demo wallet, seeded counterparties, and a guided task list.
- Clearly label every screen “Demo Simulation.”
- Data expires (for example 24 hours) or resets; no demo history is promoted to a permanent account automatically.
- Throttle by device/session/IP risk signals; never rely on demo balances for production reporting.

### Suggested guided demo

1. View a 10,000 CC simulated balance.
2. Copy or scan a recipient address.
3. Send 25 CC; review simulated fee.
4. Observe queued and confirming states.
5. Open transaction in Explorer.
6. Receive CC from a seeded participant.
7. Complete with a plain-language recap.

### Learning/help layer

- Contextual “What does this mean?” panels alongside addresses, fees, confirmations, blocks, and statuses.
- Help Center articles are short, task oriented, and cross-link to practical actions.
- Glossary with definitions written separately for general crypto concepts and Coin Caret’s implementation.
- Optional lesson progress and quizzes; quizzes must not represent credentials unless separately designed.
- Support flow: Help search → article → contact form. Preserve screen context as non-sensitive metadata with consent.

## 13. Notifications

### Channels

- In-app notification center: default channel for all non-critical events.
- Transactional email: verify email, password reset, new-device/security alerts, optional transaction completion.
- Later mobile push via platform permission, using the same notification preference model.

### Notification events

- Welcome/onboarding, email verified.
- Incoming simulated transfer submitted/confirmed.
- Outgoing transaction queued, confirmed, failed, cancelled, or reversed by administrative compensating action.
- Simulated withdrawal requested, approved, rejected, or completed.
- Security events: password changed, MFA changed, new session, account suspension.
- Admin/cohort invitations where enabled.
- Network maintenance notices and status incidents.

### Requirements

- Notifications must use safe, non-sensitive summaries and deep-link only after authentication.
- Deduplicate noisy state changes and respect user preferences, except essential security/legal notices.
- Maintain delivery status and retry policy; do not expose email addresses or details in public logs.

- Show impersonation only as a tightly controlled, logged, time-limited support mode with a visible banner; do not allow transactions during impersonation by default.

## 15. Roles and RBAC

Use explicit permissions, not only role labels. Enforce authorization in the API and database policies, not just the UI.

| Role | Typical permissions |
|---|---|
| Platform owner | Full configuration and administrator management; use sparingly. |
| Operations admin | Users, wallets, transactions, requests, approved issuance within limits. |
| Finance/simulation operator | Issue/adjust CC, configure permitted fee settings, review supply reports; no user security administration. |
| Support agent | Read limited user context, manage tickets, suspend per policy; no ledger adjustment or network controls. |
| Content editor | Draft/edit learning and public content; no publish without publisher permission if workflow enabled. |
| Analyst | Read aggregate reports and approved exports; no personal-data export by default. |
| Auditor | Read-only access to audit/ledger/reporting views. |
| User | Own profile, wallet, transactions, settings. |
| Demo user | Segregated temporary access only. |

Define permissions such as `ledger.adjust.create`, `ledger.adjust.approve`, `network.pause`, `network.settings.update`, `users.suspend`, `reports.export.pii`, and `audit.read`. Default deny; review permissions on every role change.

### Key relationships

                 └──< LedgerAccount ──< LedgerEntry >── Transaction

### Integrity constraints

- Each transaction’s postings must balance to zero per asset.
- Amounts are fixed-point integers in smallest unit; never use floating point for balances/fees.
- Unique `public_id`, unique active address, unique block height, unique synthetic hash, and unique idempotency key within initiator/scope.
- Status transition checks; a confirmed transaction cannot be edited.
- No ledger entry update/delete permission for application roles; corrections require a new compensating entry.

## 17. Backend and API architecture

### Recommended stack

- **Web:** Next.js, TypeScript, React, server-rendered public pages plus authenticated app routes.
- **API/services:** TypeScript service layer (Next.js route handlers/BFF initially or separate NestJS/Fastify service as scale requires). Keep domain logic independent of UI.
- **Database:** PostgreSQL with migrations, transactions, read replicas later if needed.
- **Auth:** managed auth provider or hardened custom auth integrated with PostgreSQL; MFA and secure sessions required for admins.
- **Jobs/queues:** Redis-backed or managed durable queue for block generation, confirmation processing, notifications, exports, and email.
- **Storage:** encrypted object storage for limited exports/assets; signed URL access.
- **Observability:** structured logs, error tracking, metrics, tracing, uptime/status monitoring.

Supabase/PostgreSQL is a reasonable early implementation path if Row Level Security, migrations, background jobs, and service-role access are carefully separated. A separate domain service should remain possible without changing the public API contract.

### Service boundaries

- Identity and access service.
- Wallet/ledger service.
- Transaction orchestration service.
- Simulation network/block processor.
- Notification service.
- Content/help service.
- Admin/reporting service.
- Audit/event service.

## 18. Security, privacy, and abuse prevention

### Security baseline

- TLS, HSTS, secure headers, CSP, dependency scanning, secret management, least-privilege infrastructure identities.
- Strong password policy, breached-password screening, rate limiting, bot protection, verified email, secure reset flow.
- MFA mandatory for all admin roles; enforce reauthentication for high-impact admin operations.
- Server-side RBAC and row-level data authorization. Test object-level authorization on every resource endpoint.
- Encryption in transit and at rest; field-level protection for sensitive data where needed.
- HttpOnly secure session cookies; CSRF protection; short session lifetime and rotation.
- Strict input validation, output encoding, parameterized queries, safe file-upload policy, content moderation for public contact submissions.
- Security event logging, alerting for unusual login/admin/issuance patterns, and an incident response runbook.

### Simulation-specific controls

- Separate demo and production namespaces/accounts; prevent cross-namespace transfer.
- No external address routing, blockchain integration, payment collection, or crypto purchase endpoints in V1.
- Hard feature flags/allowlists for any future integration; legal and security approval required before enablement.
- Configurable user and cohort send limits prevent automated abuse or confusing demonstrations.
- Avoid public PII in Explorer, email notifications, URLs, logs, or support tools.

### Privacy requirements

- Define data inventory, lawful basis/consent handling, retention schedule, access/deletion/export workflow, DPA/vendor review, and regional requirements with counsel.
- Minimize collection. Do not request government IDs, wallet seed phrases, or financial information for this simulator.
- Version and record acceptance of Terms, Privacy, and Simulation Disclosure.

## 19. Validation rules and edge cases

### Business validation

- Sender account active; wallet active and unfrozen; asset active; recipient address active and in same namespace.
- Amount is numeric fixed-point, positive, within decimal precision, above minimum, below configured per-transaction/daily limits.
- Available balance covers amount + authoritative fee. Pending/reserved balance cannot be spent.
- Sender cannot send to the same wallet in V1 unless explicitly enabled as a teaching case; otherwise show explanation.
- Quote must be fresh, tied to user/wallet/amount/recipient, and unexpired. Requote on material input or fee-settings change.
- Idempotency prevents duplicate sends on refresh/double click/retry.
- Admin adjustments require reason and allowed permission; approvals cannot be performed by the requester when dual control applies.

### Edge cases to design and test

| Scenario | Expected behavior |
|---|---|
| Double submit/send retry | Return original transaction via idempotency key; never debit twice. |
| Balance changes after quote | Revalidate at confirmation; show fresh quote/insufficient funds. |
| Network paused after submission | Keep queued under published policy or fail/release reservation; notify user. |
| Recipient frozen/suspended | Reject before submit or fail safely based on policy; do not reveal unnecessary account details. |
| Block worker delayed | Status remains queued/confirming; show delay and status page, never fake completion. |
| Processor retries | Idempotent job handling and unique constraints prevent duplicate blocks/postings. |
| Fee configuration changes | Existing valid quote remains only until expiry; transaction stores applied fee snapshot. |
| Admin error after confirmation | Create reviewed compensating transaction; no historical overwrite. |
| Email delivery failure | In-app event persists; retry email and record delivery outcome. |
| Demo expiration | Explain expiration; deny access cleanly and offer a new demo or registration. |
| Browser offline mid-send | No client-side claim of success; recover status by idempotency/transaction lookup. |
| Address typo/scan malformed | Inline validation; no send until backend confirms destination. |

## 23. Environments, deployment, observability, and backups

### Environments

| Environment | Purpose | Data rules |
|---|---|---|
| Local | Developer feature work | Seeded synthetic data only. |
| Development | Shared integration | Synthetic/resettable simulation data. |
| Staging | Release candidate and QA | Production-like config, synthetic or carefully anonymized data only. |

### Observability

- Correlation IDs from client/API/job through ledger and notification events.
- Structured logs with PII redaction; metrics for API error rate/latency, queue depth, block interval, confirmation time, job retry/dead-letter count, auth failures, issuance/adjustment alerts.
- Error tracking, distributed tracing, uptime checks, synthetic send flow in a dedicated monitoring tenant, and public status page.

### Backup and recovery

- Automated encrypted database backups and point-in-time recovery; documented retention and restoration testing.
- Object-storage versioning and backup for exports/content assets.
- Restore drills at least quarterly; verify ledger reconciliation after restoration.
- Maintain incident, disaster recovery, and customer communication runbooks. Define RPO/RTO with business owners before launch.

## 24. Testing and QA plan

### Ledger reconciliation tests

- Every committed business transaction balances by asset.
- Sum of available + pending + system accounts equals total issued less retired supply as defined.

- Confirmed transaction history is immutable; compensations are linked and visible.

### Release gates

- No P0/P1 defects; approved security/accessibility/legal review; ledger reconciliation clean; backup restore tested; monitoring/alerts live; rollback verified; product owner acceptance recorded.

## 27. Acceptance criteria

### Product integrity

- A user can never use CC for real money, redeem it, send it externally, or claim a transaction has settled on a blockchain through any V1 UI/API path.
- Simulation disclosure is present and understandable in the required locations.
- All balances displayed to users are backend-authoritative and reconcile to immutable ledger entries.

### Core user journey

- A verified user can view their CC wallet/address, receive a simulated transfer, send CC internally after a transparent fee quote, observe state changes, and open the final record in Explorer.
- Insufficient-balance, invalid-address, delayed network, failed send, and duplicate-submit cases provide accurate recovery guidance with no duplicate debit.
- Demo user can complete the guided loop in a segregated environment and understands expiration/reset behavior.

### Admin operations

- Authorized staff can issue/adjust CC, manage users/wallets, review simulated withdrawal requests, configure permitted network settings, and access reports according to RBAC.
- Sensitive admin operations capture actor, time, reason, target, before/after context, and correlation ID; configured dual approval works.
- No standard admin role can silently alter ledger history.

### Quality and readiness

- Key user/admin workflows are responsive, keyboard operable, screen-reader labelled, and meet agreed WCAG 2.2 AA checks.
- Automated tests cover ledger integrity, authorization, idempotency, transaction lifecycle, and critical end-to-end flows.
- Monitoring, backup/recovery, status page, incident runbooks, and release gates are live and tested before production.
